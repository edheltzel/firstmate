## 1. Mechanism inventory

### M0. Discovery and precise-trigger loading

**What it does.** Every skill declares a natural-language `description`, `user-invocable`, and `metadata.internal`. Five skills are directly invocable (`afk`, `bearings`, `status-report`, `stow`, `updatefirstmate`); 11 are agent-only. `AGENTS.md` carries one-line trigger instructions for the agent-only set and separate lifecycle trigger lines for the user-facing set.

**Where.** Frontmatter in every `.agents/skills/*/SKILL.md`; agent-only trigger list at `AGENTS.md:450-468`; examples of lifecycle triggers at `AGENTS.md:181,211,216,352,450`.

**Dependencies / dependents.** Depends on the host harness discovering `.claude/skills -> ../.agents/skills` and honoring skill metadata. Every procedure below depends on the model noticing the trigger and loading the file.

**Why it exists.** `firstmate-coding-guidelines` says conditional detail belongs in a skill to avoid charging every session its token cost, and that a skill without an inline trigger is dead weight (`.agents/skills/firstmate-coding-guidelines/SKILL.md:18-32,51-67`).

**Enforcement.** The loader metadata controls discoverability/direct invocation, not trigger occurrence. Repository-wide code search found no trigger observer or skill-loader call. The strongest checks are static tests that assert exact prose and one trigger entry (`tests/fm-instruction-owners.test.sh:20-42`). `bin/fm-brief.sh:166,294` explicitly tells a worker to load `decision-hold-lifecycle`, but still relies on worker compliance; only the later completion outcome is mechanically gated.

### Prose/code mismatches and ownership defects

1. **“Precise trigger” means precise prose, not precise execution.** The test proves one exact `AGENTS.md` entry exists; it cannot prove the model loaded the skill at the trigger (`tests/fm-instruction-owners.test.sh:20-42`).
2. **The skill corpus violates its own “mechanics belong in code/header” rule.** `firstmate-coding-guidelines` assigns exact flags/commands/paths to script headers and `--help` (`SKILL.md:18-32`), yet `afk`, `harness-adapters`, `secondmate-provisioning`, and `fmx-respond` restate hundreds of lines of exact mechanics.
3. **Static owner tests make drift visible only where someone anticipated the exact phrase.** They preserve textual owners but do not establish behavioral enforcement; the recovery and no-mistakes ownership gaps survived those tests.
4. **The current target conflicts with the decided Herdr-only direction.** Claude's persona says Herdr is the orchestration surface (`Themis.md:47`), but Pi and OMP say native subagents are the portable default and Herdr is conditional (`pi-themis/extensions/themis.ts:77`; `omp-themis/src/main.ts:120`). The porter must settle this before placing harness knowledge.

## 4. Coupling notes

1. **Skills are not executable units.** Loading injects text; the scripts own mechanics. A porter must not treat “we copied the skill” as implementation evidence.
2. **The trigger map and frontmatter form one discoverability contract.** Static tests require one precise `AGENTS.md` entry for selected skills (`tests/fm-instruction-owners.test.sh:20-42`). If the target uses a generated manifest, make that manifest the single owner instead of retaining two hand-written copies.
3. **Decision completion is a three-part mechanism.** The skill owns semantic inventory, `fm-decision-hold.sh` owns identities/transitions, and teardown owns the final verify call. Copying any one alone loses either decisions or cleanup safety.
4. **Recovery depends on brief immutability and cleanup safety.** Report 04 proved same-brief relaunch depends on `fm-brief.sh` refusing overwrite; report 06 proved external Treehouse return provides no safety because donor teardown always uses `--force`. The recovery skill cannot be ported independently of the brief and landed-work predicates.
5. **Status reports depend on the state model, not on Markdown wording.** Both report skills consume `fm-bearings.v1`; moving to GitHub Projects requires rebuilding the canonical snapshot first. Do not copy the rendering prose and then improvise its inputs.
6. **Harness facts have four owners today:** skill prose, spawn code, backend composer/busy code, and dated backend docs. The port should use one typed adapter table for machine facts, docs for evidence, and a small skill only for manual operator actions.
7. **`firstmate-coding-guidelines` is correct about one-owner placement and violates it in its own skill system.** Exact mechanics repeated in `afk`, `harness-adapters`, `secondmate-provisioning`, and `fmx-respond` should collapse to script help or generated references.
8. **Durability policy changes several otherwise-surviving skills.** `project-management`, `decision-hold-lifecycle`, `stow`, `bearings`, and `status-report` all assume gitignored private home files. The decided target says durable plans, reports, and decisions are committed; do not copy their destination paths.
9. **The target's existing tool guard is the enforcement chokepoint.** Pi and OMP already block writes/shell mutations (`themis.ts:236-256`; `main.ts:296-310`). Report 05 identified it as the natural home for no-mistakes ownership enforcement; the same hook can enforce lock/read-only mode, prohibited lifecycle calls, and other observable skill rules rather than adding more prose.
10. **Resolve the target delegation contradiction first.** The Claude persona is Herdr-first, while Pi/OMP make native subagents primary. Harness, status, recovery, and cleanup placement all depend on which endpoint model is authoritative.
11. **Vocabulary is cross-cutting.** Surviving content must replace captain/firstmate/crewmate/Fleet/secondmate language with Ed/Themis/worker/reviewer/explorer, including generated briefs and error text, not only skill headings.
12. **Do not carry phrase-presence tests as behavioral proof.** Keep owner-map tests if useful, but add integration tests at the actual chokepoints: trigger dispatch, launch refusal, decision completion, recovery ownership, and cleanup safety.
